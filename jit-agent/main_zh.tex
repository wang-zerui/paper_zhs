\begin{abstract}
智能体能力并非仅由模型决定。智能体支架涵盖记忆管理、规划策略、动作协议以及工具/技能编排，其作用可能压过底层基础模型本身的贡献。然而，支架设计仍依赖人工、针对特定任务，因而从根本上难以扩展。我们提出 \ourmethod：一种支架智能模型，经过训练后可为任意现成的智能体大语言模型即时合成适应任务的智能体支架。我们将智能体支架形式化为一种可组合、可由机器生成，并受固定四模块协议约束的工件；随后训练 \ourmethod 针对手头任务\textit{定制支架}，为稳定可靠的执行\textit{修复支架}，并从不断扩充的既往支架配置档案中提炼性能信号以实现\textit{自我演化}。在 \ourmethod 作为支架助手的情况下，DeepSeek-V4-Flash 在 DeepSearchQA 和 OdysseyBench 上分别超过 GPT-5.6 $9.1$ 和 $4.3$ 分，而本已强大的 GLM-5.2 最多还能提升 $20.2$ 分。在受控评测中，\ourmethod 生成的支架在性能上可与 OpenCode、Claude Code 等成熟智能体运行时竞争，并能持续改善 DeepSeek V4、Mimo-V2.5 和 Qwen3.6 各种规模的模型。就我们所知，\ourmethod 是首个专为即时支架生成而构建的模型；它确立了支架智能这一与模型扩展正交、可训练、可迁移且能持续积累的智能体能力维度。 \\[0.5em]\githubicon\;代码：\ghlink
\end{abstract}

\section{引言}
\vspace{-0.5em}

\label{sec:introduction}
{智能体支架至关重要。}
大语言模型智能体的能力由两个紧密耦合的因素共同决定：产生推理与动作的\textit{基础模型}，以及将该模型置于闭环执行环境中的\textit{智能体支架}~\citep{meng2026agent,zhou2026externalizationllmagentsunified,ning2026code}。
支架决定保留哪些历史、如何形成局部意图、暴露哪些工具或技能、如何执行动作，以及何时触发验证或恢复~\citep{meng2026agent,zhou2026externalizationllmagentsunified}。
强模型若置于错误的记忆、规划器或动作协议之后也可能失败；反过来，强支架也只有在模型能够理解并遵循它时才能释放能力~\citep{lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven}。
因此，智能体智能并非模型权重独有的属性，而是模型--支架组合的属性~\citep{lee2026metaharnessendtoendoptimizationmodel,zhou2026externalizationllmagentsunified}。
由此，支架设计不是实现细节，而是决定智能体性能的一阶因素~\citep{meng2026agent,lin2026agenticharnessengineeringobservabilitydriven}。

\vspace{-0.5em}
\paragraph{预先（AOT）支架。} 上述观察催生了越来越多关于测试时支架优化的研究~\citep{lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven}。
近期系统从轨迹和反馈中优化支架代码、提示、工具、记忆、技能或控制策略，在编码、终端使用、Web 交互和通用智能体领域取得了显著改进~\citep{lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven}。
尽管这些方法彼此不同，许多方法都共享一个\textit{预先}（Ahead-of-Time, AOT）假设：将支架视为在经验流上持续优化的耐久工件，并期望所得工件能够泛化至未来的任务、领域或模型版本~\citep{lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven}。
当部署分布稳定且同质时，这是一个强大的范式~\citep{lin2026agenticharnessengineeringobservabilitydriven,zhang2025memevolve}。
然而，它仍要求优化环在看到每个未来问题的确切结构之前，预先编译出一个普遍有用的支架~\citep{lee2026metaharnessendtoendoptimizationmodel}。




\vspace{-0.5em}
\paragraph{即时（JIT）支架。} 我们转而采用一种\textbf{\textit{即时}（Just-in-Time, JIT）的支架构建观}。
不同任务显然需要不同的支架先验。
广域搜索任务可能受益于并行证据探索~\citep{qin2025flashsearcherfasteffectiveweb}；终端任务通常更适合精简、串行的 ReAct 环~\citep{yao2023reactsynergizingreasoningacting,merrill2026terminalbenchbenchmarkingagentshard}；深度研究任务需要围绕检索证据维护工作记忆~\citep{hu2025memoryageaiagentssurvey}；而 NL2Repo 风格的编码任务则天然由文件系统居中协调，文件系统存放补丁、测试、轨迹和仓库状态~\citep{yang2024sweagentagentcomputerinterfacesenable,ning2026code}。
简言之，合适的支架不仅取决于领域，还取决于具体实例~\citep{meng2026agent,zhou2026externalizationllmagentsunified}。
面对这些异质需求，优化单个 AOT 支架十分繁琐：系统必须搜索庞大的设计空间、积累足够多的轨迹，然后期待所得支架恰好适配下一项任务~\citep{lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven}。
我们由此追问另一种可能性是否可行：\textbf{模型即支架（Model-as-a-Harness）}，即由训练过的元智能体现场生成任务专用支架，再由任意智能体大语言模型在该支架下执行。

\vspace{-0.5em}
\paragraph{JIT-Agent。} 我们提出 \ourmethod，一种用于即时支架生成与演化的紧凑元智能体。
在推理时，\ourmethod{} 接收任务规范、协议、可执行工具/技能注册表，以及检索得到的一小段既往支架上下文，并输出为手头任务量身定制的可执行支架。
所得支架包装一个现成的智能体大语言模型并负责执行。随着反馈与轨迹不断积累，\ourmethod{} 可修订支架并更新支架档案，从而在生成器本身保持固定的情况下实现测试时支架演化。
训练这样的系统面临三项挑战：
\ding{182} \textbf{适应性}，即如何让生成的支架匹配任务；
\ding{183} \textbf{可靠性}，即如何保证行为可执行，并在合成失败时恢复~\citep{pan2026natural,ning2026code}；以及
\ding{184} \textbf{可演化性}，即如何将执行反馈转化为未来更强的支架~\citep{lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven}。
这三项要求共同定义了我们所说的\textbf{支架智能}：

\begin{insightbox}{支架智能}
支架智能是构建并完善模型赖以行动的运行脚手架的能力。它有三个决定性属性：\textbf{适应性}，使支架匹配任务与骨干模型；\textbf{可靠性}，产生可执行行为，并在合成失败时恢复；\textbf{可演化性}，将执行反馈转化为未来更强的支架。固定支架内的能力抵达边界之处，正是支架智能开始之处。
\end{insightbox}

\ourmethod 在协议诱导的支架空间上采用三阶段训练方案来实现支架智能~\citep{meng2026agent,zhou2026externalizationllmagentsunified}。
首先，我们将智能体支架分解为由\textit{记忆}、\textit{规划}、\textit{动作}和\textit{能力编排}模块组成的四元组，并构建 \textsc{HarnessFactory}：在这一公共接口下汇集代表性脚手架的统一代码库~\citep{hu2025memoryageaiagentssurvey,erdogan2025plan,yao2023reactsynergizingreasoningacting,xu2026agentskillslargelanguage}。
遵循“\textit{代码承载支架}”的观点~\citep{ning2026code,pan2026natural}，这一表示使支架生成成为可能：\ourmethod{} 生成结构化的可执行模块，而不是不受约束的智能体程序。
随后，\textbf{\ding{182} 阶段 I} 从教师生成的协议合规样例中学习任务条件化定制，使生成器在共享设计空间中具备适应性。
其次，\textbf{\ding{183} 阶段 II} 将失败的生成结果转化为有界修复轨迹，把编译器错误、接口不匹配和运行时故障变成可靠恢复的监督信号。
第三，\textbf{\ding{184} 阶段 III} 引入\textit{演化式组解耦策略优化}（Evolutionary Group-Decoupled Policy Optimization, Evo-GDPO），分别归一化奖励、延迟和成本，同时优化 \ourmethod{}，使其提出能够超越当前档案前沿的支架。
这一步把测试时支架改进从外部搜索启发式转变为训练所得能力，从而提供可演化性。
通过这条流水线，我们训练得到 \textbf{JIT-Agent-27B}，一种能够定制、修复和演化任务专用支架的\textbf{支架智能模型}，将支架工程从 AOT 工件转向原生 JIT 合成。

\vspace{-0.5em}
\paragraph{实验发现。}
在九个基准上，\ourmethod 持续增强其底层骨干模型：DeepSeek-V4-Flash 在 DeepSearchQA 和 OdysseyBench 上分别超过 GPT-5.6 $9.1$ 分和 $4.3$ 分，而 GLM-5.2 最多提高 $20.2$ 分。生成的支架也能与成熟运行时竞争，并可迁移至 DeepSeek V4、Mimo-V2.5 和 Qwen3.6。

\vspace{-0.5em}
\paragraph{贡献。} （I）我们将\textit{模型即支架}形式化，并把\textit{支架智能}定义为通过学习获得的、构建、修复和演化智能体运行脚手架的能力。（II）我们以 \ourmethod 实例化该范式，将四模块可执行协议、\textsc{HarnessFactory} 与定制--修复--演化三阶段流水线相结合；（III）我们验证了 JIT 生成的支架能够改善多种骨干模型，同时与强大的生产级支架保持竞争力。

\section{相关工作}
\vspace{-0.5em}
\paragraph{支架工程与模块化。} 支架已扩展到多种形态，包括 Claude Code、Codex、Hermes 和 OpenClaw 等编码与通用运行时~\citep{githubGitHubAnthropicsclaudecode,openaiCodexCoding,nous2026hermes,openclaw2026}、具身系统~\citep{zhang2026harnessvla,lee2026physicalaiharness}、搜索智能体~\citep{apodex2026,qin2025flashsearcherfasteffectiveweb}，以及以记忆为中心的系统~\citep{chhikara2025mem0,hu2026evermemos,zhang2025memevolve}。尽管各领域的实现不同，它们都包含一个支配记忆、规划与控制、动作验证以及工具/技能编排的运行层，使能力成为模型--支架组合而非模型单独的属性~\citep{meng2026agent,zhou2026externalizationllmagentsunified,pan2026natural}。模块化表示通过显式接口暴露这些选择，使各组件能够独立替换与优化~\citep{chen2026harnessx,ning2026code}。因此，我们采用紧凑的可执行分解 $\mathbf{h}=(\mathbf{M},\mathbf{P},\mathbf{A},\mathbf{F})$，分别表示记忆、规划、动作和能力编排。
\vspace{-0.5em}
\paragraph{支架优化。} 有了显式接口，支架构建便从固定的工程选择转变为针对可执行工件的优化问题~\citep{khattab2023dspy,yuksekgonul2024textgradautomaticdifferentiationtext,hu2024adas,shang2024agentsquare}。近期方法把优化范围从提示和工作流图扩展到完整支架代码，通常采用“诊断--提议--验证”循环：轨迹指导编辑，而验证决定是否保留候选~\citep{zhang_aflow_2024,lee2026metaharnessendtoendoptimizationmodel,lin2026agenticharnessengineeringobservabilitydriven,chen2026harnessx}。递归式、层次式和在线变体改进了这一循环，但仍主要依据累积经验优化持久工件，因此相对于新的任务实例仍属于预先方法~\citep{lee2026recursiveharness,zhou2026hierarchicalselfimprovement,nie2026tthe,shao2026harnessr1}。\ourmethod 则把搜索摊销到训练所得的生成器中，由其即时构建任务条件化支架；\Cref{tab:harness_optimization_comparison} 总结了这一区别。
\vspace{-0.5em}
\section{统一支架代码库}
\vspace{-0.5em}
\label{sec:harness_codebase}

\vspace{-0.5em}
\subsection{模块化支架设计空间}
\vspace{-0.5em}
智能体支架是将基础模型转化为闭环智能体的运行层~\citep{202604.0428,zhou2026externalizationllmagentsunified}：它决定保留既往交互中的哪些内容~\citep{hu2026memoryageaiagents}、如何形成中间指令~\citep{cao2025largelanguagemodelsplanning}、每个阶段暴露哪些外部能力~\citep{xu2026agentskillslargelanguage,yang2026efficientagentsmemorytool}，以及如何推进控制。因此，支架生成定义在程序而非不受约束的文本之上。我们区分原始生成空间 $\mathcal{G}$、语法有效的支架 $\mathcal{H}^{\mathrm{syn}}$、符合协议的支架 $\mathcal{H}_{\boldsymbol{\Pi}}$ 及其中的可执行子集 $\mathcal{H}^{\mathrm{exec}}_{\boldsymbol{\Pi}}$，它们满足 $\mathcal{G}\supseteq\mathcal{H}^{\mathrm{syn}}\supseteq\mathcal{H}_{\boldsymbol{\Pi}}\supseteq\mathcal{H}^{\mathrm{exec}}_{\boldsymbol{\Pi}}$。固定协议 $\boldsymbol{\Pi}$ 规定模块模式与接口、模块生命周期、验证规则和共享执行语义。它消除了语言和运行时中的偶然差异，同时保留区分现有支架的主要运行选择~\citep{autogen,githubGitHubAg2aiag2,githubGitHubLangchainailanggraph,luo2025largelanguagemodelagent}。
\ourmethod 通过四个可互操作模块显式表达这些选择：\textit{如何压缩历史}、\textit{如何形成局部意图}、\textit{如何编排工具与技能}，以及\textit{如何推进控制}。令 $\boldsymbol{\tau}$ 为一项任务，$\pi_{\psi}$ 为冻结的骨干执行器，$\mathcal{C}_{\tau}$ 为该任务可用的能力注册表（\textit{例如}工具、API 和技能）。使用 $\pi_{\psi}$ 运行支架 $\mathbf{h}$ 会产生闭环轨迹
\begin{equation}
\label{eq:trajectory}
    \boldsymbol{\xi}
    \sim \operatorname{Rollout}(\boldsymbol{\tau},\pi_{\psi},\mathbf{h},\mathcal{C}_{\tau};\boldsymbol{\Pi})
    = \bigl(\mathbf{s}_1,e_1,\mathbf{o}_1,\ldots,\mathbf{s}_T,e_T,\mathbf{o}_T\bigr),
\end{equation}
其中，$\mathbf{s}_t\in\mathcal{S}$ 是所维护的控制器状态，$e_t\in\mathcal{A}=\mathcal{U}\sqcup\mathcal{Y}$ 是来自 $\mathcal{U}$ 的可执行调用或来自 $\mathcal{Y}$ 的终止输出，$\mathbf{o}_t\in\mathcal{O}$ 是所得观察，而 $T$ 是由协议或预算限制的停止时刻。我们的关键假设是，每个 $\mathbf{h}\in\mathcal{H}_{\boldsymbol{\Pi}}$ 都允许如下分解：
\begin{equation}
\label{eq:harness_decomp}
    \mathbf{h} \,=\, \bigl(\mathbf{M},\, \mathbf{P},\, \mathbf{A},\, \mathbf{F}\bigr)
    \in
    \mathfrak{M} \times \mathfrak{P} \times \mathfrak{A} \times \mathfrak{F},
\end{equation}
其中，$\mathbf{M}$、$\mathbf{P}$、$\mathbf{A}$ 和 $\mathbf{F}$ 分别表示记忆、规划、动作和能力编排模块，而 $\mathfrak{M}$、$\mathfrak{P}$、$\mathfrak{A}$ 和 $\mathfrak{F}$ 是各自与协议兼容的实现空间。该元组遵循上述概念分解；在运行时，其依赖顺序为 $\mathbf{M}\!\rightarrow\!\mathbf{P}\!\rightarrow\!\mathbf{F}\!\rightarrow\!\mathbf{A}$。所有模块都面向同一个冻结的 $\pi_{\psi}$ 运行，下文省略这种共同的运行时依赖。
该协议同时维护不可变事件历史 $\boldsymbol{\xi}_{<t}$ 和可变控制器状态 $\mathbf{s}_t$，二者按如下方式交互：
\begin{equation}
\label{eq:module_dynamics}
\begin{aligned}
    \mathbf{v}_t &= \mathbf{M}(\boldsymbol{\xi}_{<t},\mathbf{s}_t) \in \mathcal{V},
    && \text{历史 $\to$ 视图，} \\
    \mathbf{d}_t &= \mathbf{P}(\boldsymbol{\tau},\mathbf{s}_t,\mathbf{v}_t) \in \mathcal{D}_{\mathrm{dir}},
    && \text{视图 $\to$ 局部指令，} \\
    \mathcal{C}_t &= \mathbf{F}(\mathcal{C}_{\tau},\mathbf{s}_t,\mathbf{v}_t,\mathbf{d}_t) \subseteq \mathcal{C}_{\tau},
    && \text{以指令为条件的能力编排，} \\
    (\mathbf{s}_{t+1},e_t) &= \mathbf{A}(\mathbf{s}_t,\boldsymbol{\tau},\mathbf{v}_t,\mathbf{d}_t,\mathcal{C}_t) \in \mathcal{S}\times\mathcal{A},
    && \text{控制更新与动作发出，}
\end{aligned}
\end{equation}
其中，$\mathcal{V}$ 和 $\mathcal{D}_{\mathrm{dir}}$ 分别是视图空间和指令空间。注册表 $\mathcal{C}_{\tau}$ 包含可调用工具（\textit{例如} bash 工具、API 和 MCP~\citep{sarkar2025surveyllmagentcommunication}）以及更高层的智能体技能~\citep{xu2026agentskillslargelanguage,claudeAgentSkills}；没有显式规划器的支架仍可通过 $\mathbf{P}_{\emptyset}$ 返回的空指令 $\mathbf{d}_{\emptyset}\in\mathcal{D}_{\mathrm{dir}}$ 保持类型一致。因此，$\mathbf{M}$ 从已实现历史中构建视图，$\mathbf{P}$ 形成局部指令，$\mathbf{F}$ 激活相关能力，而 $\mathbf{A}$ 更新控制器状态并发出下一动作。共享内核 $\operatorname{Exec}:\mathcal{U}\times2^{\mathcal{C}_{\tau}}\rightarrow\mathcal{O}$ 在 $e_t\in\mathcal{U}$ 时令 $\mathbf{o}_t=\operatorname{Exec}(e_t;\mathcal{C}_t)$，在 $e_t\in\mathcal{Y}$ 时令 $\mathbf{o}_t=\bot$，其中 $\bot\in\mathcal{O}$ 是终止空观察；随后它更新 $\boldsymbol{\xi}_{\le t}=\boldsymbol{\xi}_{<t}\oplus(\mathbf{s}_t,e_t,\mathbf{o}_t)$，$\oplus$ 表示追加事件。执行从 $\boldsymbol{\xi}_{<1}=\emptyset$ 和协议规定的 $\mathbf{s}_1\in\mathcal{S}$ 开始，在 $e_t\in\mathcal{Y}$ 时终止，并得到 $y=e_T\in\mathcal{Y}$。这一分解把原本异质的程序映射到 $\mathfrak{M}\times\mathfrak{P}\times\mathfrak{A}\times\mathfrak{F}$ 中可比较的坐标：规范 ReAct 使用完整历史记忆、无显式规划器、ReAct 环和完整能力注册表；Codex、OpenCode 等工程化变体加入紧凑记忆与基于待办事项的规划~\citep{openaiCodexCoding,githubGitHubOpencodeaiopencode}；ROMA、AOrchestra 和 RLM 等递归系统则实例化子问题记忆、分解、递归动作与路由能力~\citep{alzubi2026romarecursiveopenmetaagent,ruan2026aorchestraautomatingsubagentcreation,zhang2026recursivelanguagemodels}。
基于这一模块化设计空间，我们接下来引入 \textsc{HarnessFactory}；它用于检验 $\mathcal{H}_{\boldsymbol{\Pi}}$ 的表达能力，并为 \ourmethod 的元支架设计提供多样化素材。

\section{方法}\label{sec:method}
\vspace{-0.5em}
\subsection{训练流水线}\label{sec:training}
\vspace{-0.5em}

训练遵循 \ourmethod 的推理时生命周期：先合成任务条件化支架，再恢复不稳定的生成结果，最后依据更强的档案状态在线改进。令 $\boldsymbol{\tau}\sim\mathcal{D}_{\mathrm{task}}$ 表示训练任务，$\mathcal{C}_{\tau}$ 表示其能力注册表，$\mathcal{E}_{\tau}$ 表示来自支架库的一小段参考上下文。生成上下文为 $\mathbf{c}_{\tau}=(\boldsymbol{\tau},\boldsymbol{\Pi},\mathcal{C}_{\tau},\mathcal{E}_{\tau})$，$p_{\theta}$ 据此生成支架 $\mathbf{h}\in\mathcal{G}$。冻结的执行器 $\pi_{\psi}\sim\mathcal{M}$ 评估任务奖励、延迟和货币成本，而 $\operatorname{Valid}_{\boldsymbol{\Pi}}(\mathbf{h};\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau})\in\{0,1\}$ 检查协议与执行有效性，并在失败时返回结构化诊断。三个阶段分别通过离线监督、修复轨迹学习和在线策略改进来优化该生成器。

\vspace{-0.5em}
\paragraph{阶段 I：数据准备。}\label{sec:scaffold_synthesis}
阶段 I 使用一个冻结且更强的教师模型 $q_{\phi}$，在固定四模块协议下合成适应任务的支架。对每项任务，$\mathcal{E}_{\tau}$ 包含从任务类型匹配的子集 $\mathcal{B}_0^{(d(\boldsymbol{\tau}))}$ 中采样的三个脚手架，其中 $d(\boldsymbol{\tau})$ 表示任务类型。教师接收由此形成的上下文 $\mathbf{c}_{\tau}$；只有通过协议验证和执行检查的生成结果才会保留。训练任务来自已有智能体基准和环境~\citep{wu2025webwalkerbenchmarkingllmsweb,shi2025taskcraftautomatedgenerationagentic,bai2026clawgymscalableframeworkbuilding,song2026envscalerscalingtoolinteractiveenvironments}，并辅以合成任务。

\vspace{-0.5em}
\paragraph{阶段 I：训练设置。}
我们首先对被接受的教师生成结果进行标准监督微调，训练 \ourmethod 将任务及其参考上下文直接映射为符合协议的支架。由于可执行支架在质量和效率上仍可能相差很大，我们随后在相同骨干模型与评估种子下比较候选。只有当奖励提高、两个效率维度均不退化，且至少一个效率增益为严格增益时，才保留该偏好：
\begin{equation}
\label{eq:stage1_value_gap}
\begin{aligned}
\mathbf{h}^{+} \succ_{\tau} \mathbf{h}^{-}
&\iff
r^{+} > r^{-}
\;\land\;
\ell^{+}\leq\ell^{-}
\;\land\;
\kappa^{+}\leq\kappa^{-}
\;\land\;
\bigl(\ell^{+}<\ell^{-}\;\lor\;\kappa^{+}<\kappa^{-}\bigr), \\
\Delta_{\mathrm{val}}(\boldsymbol{\tau};\mathbf{h}^{+},\mathbf{h}^{-})
&= \alpha_r (r^{+} - r^{-})
+ \alpha_{\ell}[\ell^{-}-\ell^{+}]_{+}
+ \alpha_{\kappa}[\kappa^{-}-\kappa^{+}]_{+},
\end{aligned}
\end{equation}
其中，$(r^{\pm},\ell^{\pm},\kappa^{\pm})$ 是 $(\mathbf{h}^{+},\mathbf{h}^{-})$ 的重复回合平均值，$[x]_{+}=\max(x,0)$，$\alpha_r,\alpha_{\ell},\alpha_{\kappa}\geq0$ 分别对奖励、延迟和成本差距加权。所得样本对用于监督一个标准 DPO 目标，该目标由 $\Delta_{\mathrm{val}}$ 加权，并锚定到冻结的阶段 I SFT 检查点。与生成模仿结合后，该目标在保留协议有效结构的同时，更偏好效果和效率都更高的支架。


\vspace{-0.5em}
\paragraph{阶段 II：数据准备。}
阶段 I 以协议合规为优化目标，但部分生成支架仍无法通过静态或运行时验证。阶段 II 不丢弃这些样本，而是将每个失败支架 $\widetilde{\mathbf{h}}^{(0)}$ 与结构化诊断 $\mathbf{g}^{(0)}$ 配对；诊断记录编译器错误、接口不匹配、工具调用失败或运行时异常。在第 $k$ 轮修复中，教师从补丁空间 $\mathcal{P}$ 提出结构化修订 $\Delta^{(k+1)}$；$\operatorname{Apply}$ 确定性地更新支架，随后验证产生下一份诊断。我们只保留在两轮内变得可执行的轨迹：
\begin{equation}
\label{eq:stage2_repair}
\begin{aligned}
\widetilde{\mathbf{h}}^{(k+1)}
&= \operatorname{Apply}\!\left(\widetilde{\mathbf{h}}^{(k)},\Delta^{(k+1)}\right), \qquad k\in\{0,1\},\\
K^{\star}
&= \min\Bigl\{k\in\{1,2\}:\operatorname{Valid}_{\boldsymbol{\Pi}}(\widetilde{\mathbf{h}}^{(k)};\boldsymbol{\tau},\pi_{\psi},\mathcal{C}_{\tau})=1\Bigr\}.
\end{aligned}
\end{equation}
只有当 $K^{\star}$ 存在时才构造监督样本，使语料集中于现实中可局部恢复的失败，而非需要彻底重做的情形。

\vspace{-0.5em}
\paragraph{阶段 II：训练设置。}
阶段 II 通过教师强制模仿成功修订 $\{\Delta^{\star(k+1)}\}_{k=0}^{K^{\star}-1}$ 来训练 \ourmethod。每次修订都以 $\mathbf{c}_{\tau}$ 和此前完整的支架--诊断历史 $\{(\widetilde{\mathbf{h}}^{(j)},\mathbf{g}^{(j)})\}_{j=0}^{k}$ 为条件。由于 $K^{\star}\le 2$，模型学习的是部署所需的短视野机制：利用执行反馈作出少量但高杠杆的修订，恢复符合协议的执行。

\vspace{-0.5em}
\paragraph{阶段 III：数据准备。}\label{sec:harness_evolution}
阶段 III 将\emph{测试时支架演化}视为可训练能力：\ourmethod 学会提出超越既往设计的支架，而这些支架随后会成为后续任务更强的参考。受 \citep{liu2026gdpogrouprewarddecouplednormalization} 启发，我们将所得在线目标称为\textbf{演化式组解耦策略优化}（Evolutionary Group-Decoupled Policy Optimization, Evo-GDPO）。
在第 $n$ 轮在线训练中，我们采样任务 $\boldsymbol{\tau}$，从当前支架库 $\mathcal{B}_n$ 检索既往高质量设计 $\mathcal{E}_{\tau,n}$，并形成 $\mathbf{c}_{\tau,n}=(\boldsymbol{\tau},\boldsymbol{\Pi},\mathcal{C}_{\tau},\mathcal{E}_{\tau,n})$。模型从当前回合策略中独立采样 $G>1$ 个候选；候选与检索到的设计在相同冻结执行器 $\pi_{\psi}\sim\mathcal{M}$、预算和种子下评估。检索支架中奖励最高者作为当前支架；若奖励相同，则先选择延迟较低者，再选择成本较低者，由此得到当前统计量 $(b_r,b_{\ell},b_{\kappa})$。

\vspace{-0.5em}
\paragraph{阶段 III：训练设置。}
每个候选都在执行前接受验证；经有界修复后仍无效的候选会获得最低任务奖励，同时其修复延迟和成本仍计入效率测量。对可执行候选 $i$，令 $r_i$、$\bar\ell_i$ 和 $\bar\kappa_i$ 分别表示重复回合中的奖励、平均延迟和平均货币成本。奖励通道优先；只有保持当前奖励时，效率增益才会激活：
\begin{equation}
\label{eq:stage3_reward_channel}
\begin{aligned}
R^{\mathrm{rew}}_i = r_i + \lambda_{\mathrm{evo}}\,[r_i - b_r]_{+},\;
R^{\mathrm{lat}}_i = \mathbb{I}[r_i \ge b_r]\,[b_{\ell} - \bar{\ell}_i]_{+},\;
R^{\mathrm{cost}}_i = \mathbb{I}[r_i \ge b_r]\,[b_{\kappa} - \bar{\kappa}_i]_{+},
\end{aligned}
\end{equation}
其中，$\lambda_{\mathrm{evo}}\geq0$ 控制改进奖励，$\mathbb{I}[\cdot]$ 是指示函数。Evo-GDPO 在聚合前对每个候选组内的三个通道分别归一化，防止任一通道因数值尺度而压过其他通道：
\begin{equation}
\label{eq:stage3_decoupled_adv}
\begin{aligned}
A^{m}_{i}
&= \frac{R^{m}_{i} - \operatorname{mean}(\{R^{m}_{j}\}_{j=1}^{G})}
{\operatorname{std}(\{R^{m}_{j}\}_{j=1}^{G}) + \varepsilon_{\mathrm{num}}},
\qquad m\in\{\mathrm{rew},\mathrm{lat},\mathrm{cost}\}, \\
A^{\Sigma}_{i}
&= w_{\mathrm{rew}} A^{\mathrm{rew}}_{i}
+ w_{\mathrm{lat}} A^{\mathrm{lat}}_{i}
+ w_{\mathrm{cost}} A^{\mathrm{cost}}_{i},
\quad w_{\mathrm{rew}}>w_{\mathrm{lat}}+w_{\mathrm{cost}}.
\end{aligned}
\end{equation}
这些非负权重之和为一，且上述不等式使任务奖励占主导；$\varepsilon_{\mathrm{num}}>0$ 用于稳定归一化。我们还在训练批次内归一化 $A_i^{\Sigma}$，并将其用于标准裁剪 PPO 目标，同时加入相对于冻结阶段 II 检查点的词元级 KL 惩罚。因此，与标准组相对优化不同，Evo-GDPO 奖励超越既往设计的候选，并在保持奖励时鼓励以更高效率实现超越。优化后，我们保守地更新支架库：候选只有在达到或超过当前奖励前沿，并严格改善至少一个前沿维度（奖励本身、延迟或成本）时才会保留。在训练期间，这些反馈同时更新 $\theta$ 和 $\mathcal{B}_n$；部署时，$\theta$ 保持冻结。

\vspace{-0.5em}
\subsection{推理架构}
\vspace{-0.5em}

\ourmethod 支持两种推理模式：\textit{静态推理}和\textit{流式推理}；二者的区别在于任务完成后是丢弃经验，还是保留经验以支持后续任务。

\vspace{-0.7em}
\paragraph{静态推理。}
在该模式下，我们引入一种轻量级测试时扩展方式：\ourmethod 并行生成 $N$ 个支架，从中选择一个，并且只执行选中的支架。这样可以在不增加环境回合数的情况下提高候选多样性。选中支架遵循前述相同的验证和有界修复流程。

\vspace{-0.7em}
\paragraph{流式推理。}
流式推理模式旨在让有用经验沿任务序列向后传递。对于第 $n$ 个任务 $\boldsymbol{\tau}_n$，\ourmethod 从当前支架库 $\mathcal{B}_n$ 中检索，生成并选择支架 $\mathbf{h}^{\dagger}_n$，然后执行一次。所得环境反馈仅用于判断该经验是否应更新支架库：
\begin{equation}
\label{eq:streaming_inference}
\begin{aligned}
\boldsymbol{\xi}_{n}
\sim \operatorname{Rollout}(\boldsymbol{\tau}_n,\pi_{\psi},\mathbf{h}^{\dagger}_{n},\mathcal{C}_{\tau_n};\boldsymbol{\Pi}),
\mathbf{m}_{n}
&= \operatorname{Eval}(\boldsymbol{\xi}_{n}), \\
\mathcal{B}_{n+1}
= \operatorname{Update}_{\mathrm{III}}
(\mathcal{B}_{n};\boldsymbol{\tau}_n,\mathbf{h}^{\dagger}_{n},\mathbf{m}_{n}),
\mathcal{E}_{\tau_{n+1},n+1}
&= \operatorname{Retrieve}
(\boldsymbol{\tau}_{n+1};\mathcal{B}_{n+1}),
\end{aligned}
\end{equation}
其中，$\mathbf{m}_{n}=(r_n,\bar\ell_n,\bar\kappa_n)$ 包含奖励、平均延迟和平均货币成本。按照阶段 III 的保留规则，当已完成的支架没有带来可接受的改进时，$\operatorname{Update}_{\mathrm{III}}$ 保持 $\mathcal{B}_n$ 不变；否则，保留的支架将成为后续任务的潜在参考。因此，流式推理通过不断演化的支架库迁移既往经验，既不会把环境反馈注入当前回合，也不会更新模型参数。

\section{实验与分析}
\vspace{-0.5em}
\subsection{实验设置}
\vspace{-0.5em}
\paragraph{评估基准。}
我们在覆盖四类任务的九个基准上评估 \ourmethod。\textbf{深度研究}包括 BrowseComp-Plus~\citep{chen2025browsecompplusfairtransparentevaluation}（准确率）、DeepSearchQA~\citep{gupta2026deepsearchqabridgingcomprehensivenessgap}（答案 F1）和 xBench-DeepSearch（xBench-DS）~\citep{chen2025xbenchtrackingagentsproductivity}（准确率）；\textbf{日常工作}包括 AgentIF-Oneday~\citep{chen2026agentifonedaytasklevelinstructionfollowingbenchmark}（归一化加权评分规约得分）和 PinchBench~\citep{pinchbenchBestModels}（平均分）；\textbf{规划}包括 DeepPlanning-Shopping（购物车匹配率）和 DeepPlanning-Travel（复合约束得分）子集~\citep{zhang2026deepplanningbenchmarkinglonghorizonagentic}；\textbf{工作区}包括 OfficeBench~\citep{wang2024officebenchbenchmarkinglanguageagents} 和 OdysseyBench~\citep{wang2025odysseybenchevaluatingllmagents}（二者均使用任务成功率）。这些基准共同覆盖证据密集型搜索、长视野指令遵循、约束感知规划和跨应用工作区执行。所有指标均按 $0$--$100$ 标度报告，越高越好。

\vspace{-0.5em}
\paragraph{骨干模型。}
\ourmethod 基于 Qwen3.6-27B 训练。我们主要将 \ourmethod 与 {GLM-5.2}~\citep{zai2026glm52} 和 {DeepSeek-V4-Flash-Preview}~\citep{deepseek2026v4} 组合。这些骨干提供互补的工作点：GLM-5.2 是强大的开放长视野模型，而 DeepSeek-V4-Flash 强调推理效率。为检验泛化能力，我们还使用了 Qwen3.6 和 Mimo-V2.5 系列中的其他模型。

\vspace{-0.5em}
\paragraph{基线。}
我们采用两组互补基线。第一组为广泛比较，包括原生 \textbf{Qwen3.7-Plus}~\citep{qwen2026qwen37plus}、\textbf{GLM-5.2}、\textbf{DeepSeek-V4-Flash/Pro}（均为预览版）、\textbf{Kimi K2.7 Code}~\citep{moonshot2026kimik27code}、\textbf{GPT-5.6-Sol}~\citep{openai2026gpt56}，以及 \textbf{Gemini 3.1 Pro/3.5 Flash}~\citep{google2026gemini31pro,google2026gemini35flash}。第二组固定骨干模型，将 \ourmethod 与五种可复用智能体支架比较：\textsc{Claude Code}~\citep{githubGitHubAnthropicsclaudecode}、\textsc{Codex}~\citep{openaiCodexCoding}、\textsc{OpenCode}~\citep{githubGitHubOpencodeaiopencode}、\textsc{Hermes}~\citep{nous2026hermes} 和 \textsc{NanoBot}~\citep{hkuds2026nanobot}。第一组衡量端到端竞争力，第二组则把支架设计的贡献与模型权重的贡献分离开来。

\vspace{-0.5em}
\section{结论}
\vspace{-0.5em}
我们提出了 \ourmethod：一种专门用于在推理时合成、修复和演化任务条件化智能体支架的模型。\ourmethod 以可组合四模块协议表示支架，并通过定制学习、修复监督和 Evo-GDPO 训练生成器，从而把支架构建从人工设计的预先工件转变为学习所得的能力。在深度研究、日常工作、规划和工作区任务中，JIT 生成的支架持续增强其底层骨干，能够与前沿模型及先进固定支架竞争，并改善成本--性能权衡。这些结果确立了支架智能，即调整模型赖以行动的运行脚手架的能力，是一种超越模型权重本身、可训练且可迁移的智能体能力来源。

\subsection{测试时支架演化}
\vspace{-0.5em}
\label{sec:test_time_evolution}
\ourmethod 不仅用于一次性生成支架，还会依据执行反馈改善其档案。我们比较了支架生成彼此独立的\emph{静态 JIT}，以及在整个评估流中持续检索并更新支架的\emph{流式 JIT}。

\begin{figure}[!t]
    \centering
    \includegraphics[width=\linewidth]{figures/jit_growth_curves_streaming_comparison_.pdf}
    \caption{\textbf{跨任务流的流式测试时支架演化。}
    图中展示 DeepPlanning-Shopping、DeepPlanning-Travel 和 OfficeBench 上的累积准确率（上）、每任务 API 成本（中）和每任务工具调用数（下）。虚线表示任务专用支架彼此独立生成的静态 JIT；实线表示在新任务到来时持续吸收执行反馈的流式 JIT。阴影区域表示流式轨迹周围的局部波动。流式 JIT 在三个基准上最终都取得更高的累积准确率，而 API 成本和工具使用轨迹仍依赖任务，且整体处于相近量级。}
    \label{fig:test_time_harness_evolution}
\end{figure}

\Cref{fig:test_time_harness_evolution} 表明，在 DeepPlanning-Shopping、DeepPlanning-Travel 和 OfficeBench 上，流式 JIT 的最终结果都高于静态变体。在三条任务流中，累积准确率优势都会随着执行反馈累积而显现，并一直保持到评估结束。相应的成本与工具调用轨迹说明，终点收益并不总是与更大的交互预算绑定。这一模式与 Evo-GDPO 的目标一致：只有能推进档案前沿的支架才会被保留。

\section{更多生成支架的可视化}
\vspace{-0.5em}
\label{sec:additional_harness_visualizations}
\setcounter{figure}{0}
\renewcommand{\thefigure}{\thesection.\arabic{figure}}
\renewcommand{\theHfigure}{\thesection.\arabic{figure}}
本附录以相同四模块协议生成的另外九个支架，补充 \Cref{sec:harness_visualization} 中的代表性案例。这些示例涵盖有界递归研究、约束密集的购物与旅行、分阶段 Web 生产、线索驱动研究、证据敏感检索、数值分析和工作区操作。它们并非单一执行模板的变体：\ourmethod 会选择适合每项请求结构的状态表示和控制机制，再围绕该选择实例化规划、动作、记忆和能力编排。总体而言，这些案例在执行语义而非提示措辞层面直观呈现了任务条件化的支架定制。

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/harness_atlas_reworked/trapdoor_flow.pdf}
    \vspace{-2em}
    \caption{\textbf{Trapdoor：委派工具调用背后的有界研究。} 合成的 \texttt{delegate} 能力由 \texttt{OrchestratorLoop} 截获；后者运行有界子智能体，并把提取的事实写入 \texttt{FactGraphMemory}。}
    \label{fig:harness-trapdoor}
\end{figure}

\vspace{-0.5em}
\paragraph{把深度研究表示为有界递归委派。}
\textsc{Trapdoor} 处理一个多跳身份问题，其线索横跨一段历史引文、一次大学合并、一本回忆录和一篇研究论文。在此，固定 DAG 会过早锁定尚不确定的证据路径，因此生成的支架使用 \texttt{DynamicDecomposer} 形成并修订子问题，同时为研究工具策略加入合成的 \texttt{delegate} 能力。一次 \texttt{delegate} 调用会启动私有研究子智能体；它拥有独立记忆、仅用于研究的工具和五步预算，返回答案随后作为普通观察重新进入父循环。与此同时，\texttt{FactGraphMemory} 从不断增长的历史中提取紧凑的键--值事实，使父智能体能够跨分支整合证据，而不必继承每个子智能体的全部轨迹。因此，该支架把递归研究变成专门面向这类任务的运行时原语；任务中的不确定性通过分支式证据收集解决。

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/harness_atlas_reworked/origami_flow.pdf}
    \vspace{-0.55em}
    \caption{\textbf{Origami：带折叠上下文的层次化工作。}\texttt{ROMAPlanning} 创建相互隔离的子任务；\texttt{HierarchicalMemory} 保留其轨迹与工件，而 \texttt{fold\_thought} 只在聚合前替换当前工作上下文。}
    \label{fig:harness-origami}
\end{figure}
\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/harness_atlas_reworked/turnstile_flow.pdf}
    \vspace{-0.55em}
    \caption{\textbf{Turnstile：先证据，后行程。}\texttt{TravelPlanning} 产生旅行规范和检查清单，\texttt{DataStoreMemory} 跟踪所需证据桶；只有 \texttt{is\_complete()} 成功后，\texttt{DynamicToolPolicy} 才暴露 \texttt{final\_answer}。}
    \label{fig:harness-turnstile}
\end{figure}

\Cref{fig:harness-origami,fig:harness-turnstile} 展示了两种通过记忆控制长视野执行的任务专用方式。\textsc{Origami} 必须在库存、配送、尺码、评论数和评分等耦合约束下组合一套季节性衣橱。\texttt{ROMAPlanning} 把请求分解为相互依赖的商品搜索，\texttt{HierarchicalAction} 以有界深度并行运行至多两个分支，每个分支保留自己的轨迹和工件。当某个分支变长时，\texttt{fold\_thought} 只替换其当前工作上下文；已完成子任务的结果仍可用于最终约束检查。因此，该支架把上下文预算花在组合式购物任务尚未解决的部分，同时不丢弃先前的商品证据。

相比之下，\textsc{Turnstile} 服务于一项旅行请求，其中规定了日期、乘客、房间、出发时间窗口、评分最高的酒店、景点、餐饮和每日路线。生成的 \texttt{TravelPlanning} 模块把这些义务编译为带类型的 \texttt{travel\_spec} 和收集清单，\texttt{DataStoreMemory} 则为每类证据分配专用桶。\texttt{DynamicToolPolicy} 为缺失的证据桶暴露搜索工具，但在 \texttt{is\_complete()} 成功前不会暴露 \texttt{final\_answer}。此处记忆的首要用途不是压缩长轨迹；它充当可执行覆盖契约，防止系统在收齐所需旅行事实之前合成行程。

    \label{fig:harness-pegboard}

\Cref{fig:harness-gearbox,fig:harness-pegboard} 展示了显式状态如何持续重塑后续决策。\textsc{Gearbox} 用于寻找指定行车半径内的中餐厅，并把结果发布为交互式单页指南。其 \texttt{PhaseAction} 是共享\textit{搜索--收集--构建}寄存器的唯一写入者；只有收集到足够多的结构化餐厅记录后，系统才会转入构建阶段。\texttt{PhaseToolPolicy} 和 \texttt{PhaseAwareMemory} 都读取该寄存器，从 Web 发现切换到记录检查，再切换到编码和发布，同时把观察压缩为当前阶段所需的模式。因此，模型会创建一个阶段机，因为任务的模态会从证据获取转向工件构建。

\textsc{Pegboard} 则处理一个由六条传记与电影线索定义的身份识别问题。它把进度表示为候选者 $\times$ 线索矩阵，其中每条提取出的主张都保留其文档标识符。空单元格和矛盾会驱动 \texttt{DynamicResearchPlanning} 开展定向搜索，而得到充分支持的行则触发独立验证阶段，重新打开引用文档并解决冲突。与通用研究记录不同，该状态使覆盖率和来源可追溯性能够直接驱动动作。它与 \textsc{Gearbox} 的对比说明，生成状态可以是小型阶段变量，也可以是由任务塑造的证据结构，具体取决于接下来必须由什么来支配动作。

\Cref{fig:harness-appraiser,fig:harness-abacus} 对后续推理从先前执行中接收的内容进行了定制。\textsc{Appraiser} 通过协调植物学特征与文本证据，回答一个古典本草身份识别问题。每完成一次搜索或阅读步骤，辅助评分器都会为观察赋予证据价值；\texttt{EvidenceGuidedMemory} 保留完整轨迹以供审计，但只把最早、最新和得分最高的 $K$ 项观察渲染进下一轮上下文。因此，低价值探索不再与最有助于识别的段落竞争，同时持久历史中的证据不会被删除。该支架专门适配一类检索任务：其主要瓶颈是证据显著性而非工具选择。

\textsc{Abacus} 面向一项数值分析请求生成：先比较地区平均值，再对获胜地区中的国家排名。该支架有意把聚合移出语言模型推理：\texttt{StructuredReActAction} 调用 shell 或 Python，从标准输出中提取带标记的 \texttt{RESULT\_JSON} 载荷，必要时修复其语法，再把数值写入 \texttt{StructuredStateMemory}。随后，地区、国家、地区均值和国家均值都作为带类型状态注入每个后续步骤，使最终答案报告由解释器算出的数值，而非从文本中重新推导。两个案例都保留完整审计轨迹，但会围绕各自任务的主导可靠性要求渲染工作视图：前者关注证据选择，后者关注数值保真度。

\Cref{fig:harness-player-piano,fig:harness-mulligan} 通过控制动作何时进入持久历史，为不同规模的工作区执行提供专用机制。\textsc{Player Piano} 处理配置文件的批量迁移，包括数据库、日志和 API 端点变更。\texttt{StructuredPlanning} 产生带类型的\textit{发现}、\textit{处理文件}和\textit{最终答案}步骤，由 Python 调度器执行；每次编辑后，一个确定性的非大语言模型检查决定前进还是重试。\texttt{ProgressiveTaskMemory} 把逐文件看板渲染进系统提示，并同时保留原始文件与已接受的变更，防止系统在大批量任务中忘记哪些文件真正通过了验证。

\textsc{Mulligan} 面向一个较短的文档任务生成：从 DOCX 文件中提取学生标识符，并重命名同一个文件。其线性计划不需要层次结构或上下文压缩，因此支架保留完整的成功历史，只暴露 Word 和文件操作，同时隐藏无关的电子邮件、电子表格和 PDF 工具。如果动作失败，循环会在本地追加错误，并在同一步骤重新生成，最多尝试两次；只有成功动作会在计划推进前提交。因此，两种支架都关注可靠的工作区修改，但实现方式不同：一个使用带类型的批次进度和逐文件验证，另一个使用窄工具暴露与事务式步骤修复。这种依赖任务的差异正是 \ourmethod 所追求的行为：可靠性机制根据请求的结构和失败面生成，而非作为统一脚手架强加给所有任务。
