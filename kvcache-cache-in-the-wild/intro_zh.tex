\section{引言}
\label{sec:intro}

大语言模型（LLM）凭借在多种任务上涌现出的能力，已经成为重要的云服务。面向消费者的服务（to-C），如基于对话的聊天机器人~\cite{chatgpt}，以及通过 LLM API 调用提供的企业服务（to-B），都已广泛部署在云端~\cite{openaiapi,genimiapi,claudeapi}。作为在线服务，以低延迟、高吞吐量服务 LLM 至关重要；但由于每个 LLM 请求都需要巨量计算，要以成本高效的方式实现这一目标并不容易。

缓存已服务请求的中间结果（{\kvcache}）已成为改善服务性能的常见方法~\cite{openai-cache,claude-cache}：当两个请求共享相同输入前缀时，它们的 {\kvcache} 相同；因此，若缓存第一个请求的 {\kvcache}（即 {\kvcache} 缓存），便无需为后续请求重复计算。命中时计算量减少，从而降低服务延迟并提高吞吐量。

与传统数据缓存系统~\cite{yang2020twemcache,atikoglu2012workload,180324} 类似，缓存淘汰策略等 {\kvcache} 缓存系统组件的有效性，应针对工作负载的 {\kvcache} 复用特征进行定制。然而，LLM 服务工作负载包含多样的请求类型，而且每种请求类型又具有独特特征，因而十分复杂。例如，生产级 LLM 服务既要处理 to-C 工作负载（如聊天），也要处理 to-B 工作负载（如通过 API 调用实现任务自动化）。这些请求还可能以单轮或多轮交互方式处理（第~\ref{sec:bg} 节）。由于 {\kvcache} 可跨不同单轮请求与多轮请求复用，单轮请求类型与多轮交互模式都可能影响 {\kvcache} 缓存的设计选择。

由于缺乏对真实轨迹的深入分析，人们对常见 LLM 服务工作负载中的 {\kvcache} 缓存仍存在显著认知缺口。首先，生产工作负载是否存在大量复用、哪类请求贡献最多复用，尚不明确。其次，{\kvcache} 的复用时间或复用概率分布仍然未知，而这些分布对缓存策略设计至关重要。最后，现有工作缺少对 {\kvcache} 生命周期的刻画，而该信息对于估计真实 LLM 服务所需的缓存容量不可或缺。

\stitle{刻画生产轨迹。}
为弥补上述缺口，我们从世界上最大的云服务商之一（\company）收集并刻画了两类具有代表性的生产服务工作负载：其一是 to-C 工作负载，用户通过浏览器聊天机器人或移动应用向云托管 LLM 服务提交请求；其二是 to-B 工作负载，开发者在程序中通过 OpenAI 兼容接口向 LLM 服务发送 API 请求。在公司严格隐私政策允许的范围内，我们尽可能收集了详细信息，包括请求提交时间、请求类型（单轮、多轮、API 请求或其他）以及用于分析缓存有效性的匿名化内容。据我们所知，现有其他 LLM 服务轨迹均无法同时达到本文轨迹的信息深度与规模（见表~\ref{tab:compare-traces}）。例如，ShareGPT~\cite{sharegpt} 仅提供各请求的输入和输出，而不提供请求提交时间；后者对分析真实 {\kvcache} 命中率及其随时间的使用情况至关重要。我们相信，所收集的工作负载代表了典型 LLM 服务工作负载，并能为今后的 {\kvcache} 缓存系统设计奠定基础。

从同时提高性能与资源利用效率的 {\kvcache} 缓存系统设计视角看，本文的\emph{关键结论}如下：
\begin{enumerate}[leftmargin=*,itemsep=2pt]
    \item {\kvcache} 复用十分常见，但其复用比例低于合成数据集研究中报告的数值~\cite{cachedattention,DBLP:journals/corr/abs-2403-14401}。复用呈偏斜分布：10\,\% 的 {\kvcache} 块贡献了 77\,\% 的复用。不同轨迹中的复用来源也不相同：与“多轮请求可能主导大部分复用”的直观认识相反，在 to-B 工作负载中，单轮请求贡献了 97\,\% 的 {\kvcache} 复用（第~\ref{sec:workload-patterns} 节）。
    \item 与 {\kvcache} 设计相关的关键工作负载特征，例如复用时间与复用概率分布，会随 LLM 请求类型（API 或聊天）以及多轮请求的轮次而变化。尽管存在这种多样性，但对每个具体请求类别（类型与轮次的组合），都可以根据历史信息预测复用时间（第~\ref{sec:motiv-temporal-spatial} 节）。服务系统已知请求类别，因而可系统地利用估计概率改进缓存策略。
    \item {\kvcache} 的生命周期短暂：to-B 工作负载中 {\kvcache} 生命周期的 P99 为 97 秒，因此通常只需较小缓存。例如，对使用常见 GQA~\cite{DBLP:conf/emnlp/AinslieLJZLS23} 的模型，在采用 LRU 等标准缓存淘汰策略时，to-B 工作负载中每块 GPU 配置相当于 2 倍 GPU HBM 的 {\kvcache} 容量，即可接近无限容量下的理想命中率（第~\ref{sec:analyze-capacity} 节）。
\end{enumerate}

上述刻画揭示了当前 {\kvcache} 缓存系统可能忽视的若干重要设计决策。第一，优化单轮请求缓存与优化多轮请求同等重要。第二，相比仅采用 LRU 这类工作负载无关策略，采用工作负载感知的缓存策略可以提高命中率。第三，{\kvcache} 生命周期短暂意味着最不经常使用（LFU）策略并不合适，因为一个短命 {\kvcache} 在过去也可能有很高的访问频率。与此同时，对于 API 主导的 to-B 工作负载，小型（GPU 上）缓存已经足够，从而可以免去部署和管理 CPU--RDMA--SSD {\kvcache} 存储层次的成本与复杂性。除上述主要结论外，我们还发现了一些有趣现象，例如尽管用户可能通过提示词库~\cite{prompt-library} 共享提示词，跨用户的 {\kvcache} 命中仍然极低（第~\ref{sec:workload-patterns} 节）。

\stitle{改进的 {\kvcache} 缓存淘汰策略。}
基于这些发现，我们提出了一种工作负载感知的 {\kvcache} 淘汰策略（第~\ref{sec:design-policy} 节），利用每类工作负载经分析得到的复用概率分布，提高真实工作负载下的缓存命中率。具体而言，我们使用按经验采样的各工作负载复用概率分布来确定每个 {\kvcache} 块的优先级，同时考虑刻画出的空间局部性与 {\kvcache} 生命周期。为验证改进设计的有效性，我们将策略集成到云上流行的 LLM 服务系统 vLLM~\cite{vllm} 中。基于生产轨迹的大量评估表明，与 LRU、LFU 等工作负载无关策略相比，该设计可将缓存命中率提高 3.9\,\%，并将平均响应时间最多改善 41.4\,\%。

\stitle{讨论。}
继续之前，我们说明本工作的两个局限。第一，结果基于大规模 LLM 服务工作负载为期一周的生产轨迹。虽然我们认为聊天机器人和 API 工作负载代表了当前典型情形，但 LLM 服务工作负载仍在演化，推理~\cite{openai-o1} 等新工作负载正在出现；对这些新工作负载的刻画留作未来工作。第二，我们主要关注 {\kvcache} 缓存策略设计，但认为全局调度策略等其他 LLM 服务系统组件也可能受益于这些发现；其他探索同样留作未来工作。尽管如此，我们相信“先刻画真实服务特征、再优化具体服务组件”的方法能够推广到其他 LLM 服务工作负载与系统。

本文所分析轨迹的样例见 \burl{https://github.com/alibaba-edu/qwen-bailian-usagetraces-anon}，淘汰策略的参考实现见 \burl{https://github.com/vllm-project/vllm/pull/22236}。
